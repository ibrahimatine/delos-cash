# AGENTS.md

This file provides repository-specific guidance to coding agents.

## What this is

DELOS CASH: a public directory of transparent collectes (Senegal hackathon
prototype, Code & Chain Dakar 2026). Associations and cagnottes show who
collects, what comes in, where the money goes and the proof it served the
cause. Contributions in Bitcoin Lightning, payouts in Mobile Money, through
the Bitnob sandbox: no real money. UI in French (vouvoiement); code, comments
and identifiers in English.

Read these project documents before changing product behavior:

- **Architecture**: follow the React, Vite, Hono, and SQLite patterns in this
  repository. The README has the clone, setup, and run instructions.
- **Product**: `CAHIER-DES-CHARGES.md` (v1.2, business rules RG-xx, Bitnob
  integration) and `DESIGN.md` (v1.4, screens, components, demo data).
  Current colour tokens are in `web/assets/styles/style.css`.

## Commands

Node.js 22+ and pnpm. The API uses Hono and better-sqlite3; the client uses
React and Vite.

```bash
pnpm install
pnpm dev              # :8000, Vite + React + API + SQLite (delos.db)
pnpm test             # Node test runner (.env-test: in-memory SQLite, Bitnob mock)
pnpm check            # type-check client and server
pnpm lint             # currently the same TypeScript check as pnpm check
pnpm fmt
pnpm build            # Vite production build
pnpm start            # production server (.env-prod)
pnpm icons            # PNG icons of the PWA from web/public/icons/*.svg
pnpm seed-files        # demo documents (api/seed-files/, web/lib/seed-files.ts)
pnpm backup            # copy of the database and the documents
docker compose up -d --build   # the production image on :3000 (Dockerfile)
```

Secrets (Resend key, Bitnob keys) go in `.env`, never committed: the dev
tasks read `.env-dev` then `.env`. Production reads `.env-prod`.

`pnpm dev` serves the source through Vite. Delete `delos.db` (server stopped)
to start again from the seed, or use « Réinitialiser la démo ».

## Architecture

- **Server** (`api/`): Hono handles `routeHandler` from `routes.ts`
  (every endpoint is a `route({ authorize, fn, input, output })` keyed
  `'METHOD/api/path'`, validated by local schemas), plus raw handlers:
  `GET /api/events` (SSE) and `POST /api/webhooks/bitnob` (raw body for the
  signature). Permissions are always checked on the server.
- **State** (`api/state.ts`): the whole database is held in memory, loaded
  from SQLite at boot; `mutate(fn)` runs a domain function on a copy, writes
  what changed in one transaction, then emits an SSE event. Aggregates are
  JSON documents (`person`, `organization`, `fund`, `contribution`,
  `expense`); the register is the append-only table `ledger_event`; full
  Mobile Money numbers live apart in `private_number`. Tables are created in
  `api/schema.ts`; `migrations/NNN-migration.js` only alter an existing base.
  `api/lib/db.ts` adapts better-sqlite3 to the existing tagged SQL calls.
- **Shared domain** (`web/lib/`, no DOM): `types.ts`, `rules.ts` (balances,
  statuses, rights), `domain.ts` (mutations and business rules RG-xx, throw
  `DomainError` → 400), `ledger.ts` (hash chain), `seed.ts` (DESIGN §3).
  The server runs them; the client only reads `rules.ts` through
  `web/lib/store.ts`.
- **Bitnob** (`api/bitnob.ts`): one interface, two implementations chosen by
  `BITNOB_MODE`: `sandbox` (signed HMAC-SHA256 requests, decimal strings read
  without floats) and `mock` (same state machine, paced for the demo by
  `BITNOB_MOCK_PACE_MS`). Every call goes to the `provider_call` journal.
  `api/payments.ts` orchestrates invoices, quotes and payouts; a success is
  only declared after reading Bitnob (RG-19); webhooks are verified
  (HMAC-SHA512), deduplicated by `event_id`, and only trigger a reading; the
  reconciliation job reads every pending operation.
- **E-mails** (`api/email.ts`): Resend through the server-side `fetch` API.
  Off without `RESEND_API_KEY`: the demo then returns the link token
  (`demoToken`) to open it from the screen. A signup creates nothing until
  the e-mailed link is opened (`email_token` holds only its SHA-256);
  invitations are sent in the background with `notify()` (tests await
  `flushEmails()`, Resend is mocked by `api/lib/email-mock.ts`). Every send
  goes to `email_log`, which also enforces the hourly limits.
- **Files** (`api/files.ts`): `POST /api/files` (raw body, signed in, PDF,
  JPEG or PNG read from the bytes, 5 Mo) stores a file in `FILES_DIR` under
  its SHA-256; `GET /api/files/<sha256>` serves it if a public document
  points at it, or to the people concerned (members, managers, the person
  of an identity scan) and the moderators. Routes that take a document call
  `checkedDoc`/`requireFile`: the file must have been sent first. The demo
  documents are real files generated by `task-seed-files.ts`; the seed reads
  their hashes from `web/lib/seed-files.ts`, so rerun it after editing them.
  `DropZone` (`web/ui/docs.tsx`) hashes then uploads at once.
- **Accounts**: `MODERATOR_EMAILS` makes confirmed accounts moderators; 5
  failed sign-ins lock an address for 15 minutes (`login_failure`).
- **Backups** (`api/backup.ts`): `VACUUM INTO` plus the new files, daily in
  production (`prod-server.ts`), 14 copies kept.
- **Client** (`web/`): React. `web/lib/reactive.ts` provides the small signal
  store used by existing screens; `web/lib/store.ts` holds
  the snapshot of `GET /api/state` (filtered by `api/snapshot.ts`: no private
  data of others), reloaded on every SSE event and cached in `localStorage`
  for offline reading. `web/lib/actions.ts` calls the Fetch client and refuses
  financial actions offline.
- **Routing**: the local History API router keeps clean paths, never a `#`; ids
  stay in the query string (`/collecte?id=ecole-ndiass`). Every URL lives in
  `web/paths.ts`. Dialogs use `?dialog=<id>`.
- **Demo** (`DEMO_ACCESS=1`): account switcher without password
  (`POST /api/demo/session`), reset, failure states (`/api/demo/*`), states
  through query params (`?etat=expiree|echec` on P4,
  `?etat=expiree|hors-tolerance|echec|incertain` on G4). Guided panel:
  `web/ui/demo-panel.tsx`, nine steps derived from the data; its actions
  dynamically import the functions the screens export (`payCurrentInvoice`,
  `fillExpenseExample`, `getQuote`, `confirmPayout`, `fillProofsExample`,
  `fillFundExample`): keep them exported when editing a screen.
- **Parcours de l'argent** (`web/ui/money-flow.tsx`, top of the collecte
  page): entries → the collecte (paid / committed / available) → one branch
  per spending with its four steps, beneficiary and documents. One meaning
  per line, explained by the legend: moving dashes = money went this way
  (the trunk carries the strongest state of the branches below it), fixed
  dots = reserved not paid, grey = no movement (`.flow-h` / `.flow-v` in
  `style.css`, still under `prefers-reduced-motion`). The steps inside a
  branch are progress (`.step-line`), never animated.
- **Filters** (`web/lib/expense-filter.ts`, `web/ui/expense-filters.tsx`):
  search, phase (en cours / terminées), period (a calendar: year ‹ ›, then a month, it closes; `web/ui/period-picker.tsx`) in the URL
  (`?q=&etat=&periode=`), newest first, month marks, pages of 10; shown from
  6 spendings (`FILTER_FROM`). The « Sorties » tab follows the same filters.
  Long lists scroll inside their card (`ScrollBox`, `web/ui/scroll-box.tsx`:
  at either end the wheel goes on with the page at once; sticky month marks):
  the head of the card (title, legend, filters) stays.
- **Associations over time**: a representative opens collectes for the
  association (`POST /api/organizations/funds`, page `paths.orgFund`), with
  a goal or permanent (`goal: 0`); a collecte is closed from G1
  (`POST /api/funds/close`, `FUND_CLOSED`). The association page
  (`web/ui/org-overview.tsx`) shows all its collectes together: month by
  month chart, the map association → activities, one feed of every movement
  with its filters (`?q=&sens=&activite=&periode=`).
- **Sharing** (`web/ui/share.tsx`, `api/og.ts`): « Partager » for everyone on
  collecte, association and spending pages (`?dialog=partager`); the server
  writes Open Graph tags into index.html and draws the preview image
  (`/api/og/collecte/<id>.png`, resvg, fonts in `api/og-fonts/`).
- **PWA**: `web/public/` (manifest, `sw.js` versioned by build, icons). The
  service worker is only registered by the production build and never
  touches `/api/`.

## Styling rules (Tailwind v4)

- Tailwind CSS v4, CSS-first config in `web/assets/styles/style.css`
  (`@theme`, `@custom-variant dark`), standard `class=` attribute.
- Colours are semantic tokens only (`bg-page`, `bg-surface`, `text-ink`,
  `text-muted`, `bg-accent`, `text-ok`, `bg-warn-soft`, `text-err`,
  `text-btc`…); the dark theme is a second set of values on
  `[data-theme=dark]`, no `dark:` variant needed.
- Orange (`btc`) is reserved for Bitcoin / Lightning. Every status has an icon
  and a label, never the colour alone. Fonts: Unbounded (titles, amounts),
  Bricolage Grotesque (UI), Space Mono (references, hashes, sats),
  Nasalization (logo).
- Shared building blocks are in `web/ui/` (`primitives.tsx`, `badges.tsx`,
  `money.tsx`, `people.tsx`, `expense-ui.tsx`, `docs.tsx`, `shell.tsx`…):
  reuse them before writing markup.
